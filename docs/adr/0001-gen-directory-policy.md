# ADR 0001: Commit generated code (`gen/`) to the repository

**Status:** Accepted
**Date:** 2026-10-21
**Deciders:** principal-engineer
**Related:** SMM-3 (Buf scaffold), SMM-2 (`gen/` placeholder), SMM-7 (`task gen`), SMM-8 (CI pipeline), SMM-16 (reformatted to [ADR 0000](./0000-adr-template.md))

## Context

ARCHITECTURE.md §18.1 lists `gen/` as "generated code (proto Go, sqlc),
committed or generated in CI" and leaves the choice open. `gen/` will hold:

- Protobuf/ConnectRPC Go stubs generated by `buf generate` from `api/proto`.
- sqlc-generated query code generated from `pkg/db` queries and `migrations`.

We need to decide, before any service code depends on `gen/`, whether these
artifacts are committed to version control or produced only in CI/local
builds (gitignored).

Options considered:

1. **Commit `gen/` to the repo.**
   - Pros: `go build ./...` works right after `git clone` with no toolchain
     install (no `buf`, no protoc plugins, no `sqlc` required just to build
     or read generated code). Code review and `git blame` can see exactly
     what generated code changed and when, which is useful while the proto
     contracts are still evolving quickly (Phase 0/1). Simpler CI — no
     "did codegen actually run and match" step needed before build/test.
     Consistent with the common Go ecosystem convention for protobuf repos
     (e.g. many buf-based monorepos commit `gen/`), and with how `sqlc`
     is typically used (generated queries committed next to migrations).
   - Cons: generated diffs add noise to PRs; risk of someone hand-editing
     generated code; risk of generated code drifting from source if
     regeneration is forgotten.

2. **Generate `gen/` in CI only (gitignored).**
   - Pros: no generated-code diffs in PRs; impossible for `gen/` to
     hand-drift from its source since it never persists in git.
   - Cons: every clone/build (local dev, every CI job, every `go build`)
     needs `buf` + protoc Go/Connect plugins + `sqlc` installed and a
     codegen step run first. This raises onboarding cost and couples
     "can I build the repo" to "do I have the full codegen toolchain",
     which cuts against this being Phase 0 scaffolding meant to be cheap
     to pick up.

## Decision

**Commit `gen/` to the repository.**

- `gen/` is treated as build output and must never be hand-edited — always
  regenerate via `buf generate` (and later `sqlc generate`, wired by SMM-7's
  `task gen`).
- CI (SMM-8) must add a drift check: run codegen and fail the build if
  `git diff --exit-code gen/` reports changes, so a forgotten regeneration
  is caught instead of silently shipping stale generated code.
- PR reviewers should not be expected to review generated-code diffs line by
  line; they review the source (`api/proto/**`, `pkg/db/queries/**`) and
  trust the drift check.

## Consequences

- SMM-2's `.gitignore` must **not** exclude `gen/` — verified as part of
  this story (it already did not list `gen/`, so no change was required).
- SMM-7's `task gen` target runs `buf generate` (and later `sqlc generate`)
  and leaves the output committed; it does not need a separate "clean"
  step to avoid committing generated code.
- SMM-8's CI pipeline must run codegen and diff-check `gen/` as described
  above, in addition to normal build/test/lint steps.
- If generated code size/diff noise becomes a real problem later (e.g. once
  the full §15 contract and sqlc queries land), this decision can be
  revisited in a follow-up ADR — it is not a one-way door.
